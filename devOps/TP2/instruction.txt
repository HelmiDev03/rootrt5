Pour ce TP, nous utiliserons kind (Kubernetes in Docker), car il est extrêmement léger et parfait pour simuler des clusters multi-nœuds sur une
machine locale.

🌐 Partie 3 : Le
Networking avec les Services (L'aiguillage)

Les Pods meurent et renaissent avec de nouvelles adresses IP. Le Service offre
une IP fixe et un nom DNS stable pour atteindre vos Pods.



1. Le ClusterIP (Communication Interne)

C'est le type par défaut. Il permet aux composants du cluster de se parler
entre eux (ex: un Backend qui parle à une BDD).



Action : Créez un service pour votre application web-app :



Bash

kubectl expose deployment web-app --type=ClusterIP --port=80 --target-port=80

Test : Lancez un pod temporaire "test" et essayez de contacter le
service par son nom :



Bash

kubectl run test-pod --image=curlimages/curl -i --tty --rm




•

• -curl http://web-app

2. Le NodePort (Accès Extérieur basique)

Il ouvre un port spécifique (entre 30000 et 32767) sur chaque nœud du
cluster.






Action : Modifiez le type du service en NodePort.



Challenge : Trouvez quel port a été assigné dynamiquement par Kubernetes :



Bash

kubectl get svc web-app

3. Le LoadBalancer (Le standard Cloud)

Dans un environnement Cloud (AWS, GCP, Azure), ce type commande un vrai
répartiteur de charge externe. Avec Kind, il restera souvent en <pending>
sauf si vous installez un outil comme MetalLB.
