Partie 1 · SOLID1.1 Diagnostic du code existant

Code : dossier partie1/avant/

Contexte : ShopFlow est une boutique en ligne de deux ans dont chaque évolution coûte de plus en plus cher. On audite OrderProcessor et PaymentMethod, puis on refactore sans sur-ingénierie : chaque abstraction ajoutée doit répondre à un besoin réel (YAGNI).

Le code de l'énoncé est recopié tel quel. Pour pouvoir l'exécuter, nous avons ajouté de petites classes qui simulent la base de données, l'e-mail et le SMS par un affichage (MySqlDatabase, SmtpClient, SmsGateway), une classe CreditCardPayment, et SubscriptionBilling : le module d'abonnements qui appelle recurringCharge (le commentaire // abonnements de l'énoncé).

// Code existant de l'énoncé, recopié tel quel.
public class OrderProcessor {
    public double process(Order order, String paymentType, String notifType) {
        double total = 0;
        for (Item i : order.getItems()) total += i.getPrice() * i.getQty();
        if (order.getCustomerType().equals("VIP")) total *= 0.9;

        switch (paymentType) {
            case "CREDIT_CARD": System.out.println("Débit CB : " + total); break;
            case "PAYPAL":      System.out.println("PayPal : " + total);   break;
            case "CASH":        System.out.println("Espèces : " + total);  break;
            default: throw new IllegalArgumentException(paymentType);
        }

        MySqlDatabase db = new MySqlDatabase("jdbc:mysql://localhost/shop");
        db.save(order, total);

        if (notifType.equals("EMAIL"))
            new SmtpClient().send(order.getEmail(), "Commande validée");
        else if (notifType.equals("SMS"))
            new SmsGateway().send(order.getPhone(), "Commande validée");
        return total;
    }
}
public interface PaymentMethod {
    void pay(double amount);
    void refund(double amount);
    void recurringCharge(double amount);   // abonnements
}

public class CashPayment implements PaymentMethod {
    public void pay(double a)             { /* encaissement */ }
    public void refund(double a)          { /* remboursement */ }
    public void recurringCharge(double a) { throw new UnsupportedOperationException(); }
}

SymptômeLigne ou zone concernéePrincipe SOLID violé

Immobiliténew MySqlDatabase("jdbc:mysql://localhost/shop"), new SmtpClient(), new SmsGateway() dans process() : impossible de réutiliser ou de tester la validation d'une commande sans MySQL, sans serveur SMTP et sans passerelle SMS.DIP
ViscositéURL de la base écrite en dur, aiguillages sur des chaînes : pour un nouveau besoin, le chemin le plus court est d'ajouter un case ou de copier la méthode, pas de concevoir proprement.DIP, OCP
Opacitéprocess() mélange cinq responsabilités (total, remise, paiement, enregistrement, notification) ; 0.9 est un nombre magique : « 10 % de remise VIP » n'est écrit nulle part.SRP
Répétition inutile"Commande validée" est écrit deux fois ; tout autre traitement qui dépend du moyen de paiement (remboursement, reçu…) devra recopier le même switch.SRP, OCP

Complexité inutile : absente ici, le code souffre plutôt d'un manque d'abstractions. C'est le risque à surveiller pendant le refactoring : ne créer une interface que pour un besoin réel (voir 1.3, question 3).

Partie 1 · SOLID1.2 Refactoring SRP, OCP, DIP

Code : dossier partie1/apres/

Chaque responsabilité de l'ancien process() devient une classe. OrderProcessor ne garde que l'enchaînement des étapes et ne connaît que des interfaces, rangées dans son propre package orders (le cœur métier). Les implémentations sont dans billing, notifications et persistence, et seul app.Main, le point d'assemblage, les connaît.

2OrderProcessor : enchaîner, déléguer

/**
 * Valide une commande. Sa seule responsabilité : enchaîner les étapes (SRP).
 * Chaque étape est déléguée à une abstraction reçue par le constructeur (DIP) :
 * un nouveau moyen de paiement ou un nouveau canal ne change rien ici (OCP).
 */
public class OrderProcessor {

    private final DiscountPolicy discountPolicy;
    private final PaymentMethod paymentMethod;
    private final OrderRepository orderRepository;
    private final Notifier notifier;

    public OrderProcessor(DiscountPolicy discountPolicy, PaymentMethod paymentMethod,
                          OrderRepository orderRepository, Notifier notifier) {
        this.discountPolicy = discountPolicy;
        this.paymentMethod = paymentMethod;
        this.orderRepository = orderRepository;
        this.notifier = notifier;
    }

    public double process(Order order) {
        double total = discountPolicy.apply(order, order.subtotal());
        paymentMethod.pay(total);
        orderRepository.save(order, total);
        notifier.send(order, "Commande validée");
        return total;
    }
}
  • SRP : process() fait 4 lignes, une par étape. Changer la remise, la base ou le canal ne touche plus cette classe.
  • OCP : plus de switch ni de if sur des chaînes. Un nouveau moyen de paiement est une nouvelle classe qui implémente PaymentMethod (vérifié en 1.4).
  • DIP : les quatre dépendances sont des interfaces, reçues par le constructeur. Plus aucun new d'une classe technique dans le métier.

3Les abstractions, possédées par orders

/** Abstraction : la règle de remise appliquée au sous-total d'une commande. */
public interface DiscountPolicy {
    double apply(Order order, double subtotal);
}

/**
 * Abstraction : paiement ponctuel d'une commande (encaisser, puis rembourser en cas d'annulation ou de retour).
 * Tous les moyens de paiement savent le faire.
 * Le prélèvement d'abonnement n'est plus ici : il est dans RecurringPayment (ISP).
 */
public interface PaymentMethod {
    void pay(double amount);
    void refund(double amount);
}

/** Abstraction : enregistrer une commande validée, sans dire où ni comment. */
public interface OrderRepository {
    void save(Order order, double total);
}

/** Abstraction : prévenir le client, quel que soit le canal. */
public interface Notifier {
    void send(Order order, String message);
}

Ces interfaces sont dans le package du client (orders), pas dans celui des implémentations : c'est le cœur métier qui définit ce dont il a besoin (les « ports »), et l'infrastructure qui s'adapte (les « adaptateurs »). PaymentMethod a déjà perdu recurringCharge : c'est le découpage ISP de la question 1.3.

4Les implémentations

/** Type de client : une énumération au lieu de la chaîne "VIP", une faute de frappe ne compile plus. */
public enum CustomerType {
    STANDARD,
    VIP
}

/** La règle de l'ancien code, isolée : 10 % de remise pour les clients VIP. */
public class VipDiscountPolicy implements DiscountPolicy {

    private static final double VIP_RATE = 0.10;

    @Override
    public double apply(Order order, double subtotal) {
        if (order.getCustomerType() == CustomerType.VIP) {
            return subtotal * (1 - VIP_RATE);
        }
        return subtotal;
    }
}

/** Enregistrement MySQL (simulé par un affichage). L'URL vient de l'assemblage, plus du code métier. */
public class MySqlOrderRepository implements OrderRepository {

    private final String url;

    public MySqlOrderRepository(String url) {
        this.url = url;
    }

    @Override
    public void save(Order order, double total) {
        System.out.println("MySQL (" + url + ") : commande " + order.getId() + " enregistrée, total = " + total);
    }
}

/** Notification par e-mail (envoi SMTP simulé par un affichage). */
public class EmailNotifier implements Notifier {

    @Override
    public void send(Order order, String message) {
        System.out.println("E-mail à " + order.getEmail() + " : " + message);
    }
}

Les autres classes (CreditCardPayment, PaypalPayment, CashPayment, SmsNotifier) suivent le même modèle : une classe courte par moyen ou par canal.

Partie 1 · SOLID1.3 LSP et ISP

Code : dossier partie1/apres/billing/

1LSP : CashPayment respecte-t-elle le contrat de PaymentMethod ?

Non. PaymentMethod promet que recurringCharge(amount) prélève le montant. CashPayment lève une exception pour n'importe quel montant : elle ne peut donc pas remplacer un PaymentMethod partout où on en attend un. C'est exactement ce qu'interdit LSP : un sous-type ne doit pas casser ce que le client attend du type de base.

Code client qui échoue à l'exécution : tout code qui appelle recurringCharge() sur un PaymentMethod sans connaître sa classe. C'est le cas du module d'abonnements :

/**
 * Code client existant (module abonnements) : prélève chaque mois tous les abonnés.
 * Il est écrit pour l'interface PaymentMethod : il fait confiance à son contrat.
 */
public class SubscriptionBilling {

    public void chargeAll(List<PaymentMethod> subscribers, double monthlyFee) {
        for (PaymentMethod method : subscribers) {
            method.recurringCharge(monthlyFee);
        }
    }
}

2ISP : découpe de PaymentMethod par client

InterfaceMéthodesClientImplémentée parPackage
PaymentMethodpay, refundLe traitement des commandes : OrderProcessor encaisse, une annulation rembourseCB, PayPal, espèces, cryptoorders
RecurringPaymentrecurringChargeLe module d'abonnements : SubscriptionBilling prélève chaque moisCB, PayPalbilling

Chaque interface est rangée à côté de son client (DIP : l'abstraction appartient à celui qui l'utilise). Une classe implémente les deux si elle sait faire les deux :

/**
 * Prélèvement d'un abonnement. Son client : SubscriptionBilling.
 * Seuls les moyens qui savent le faire l'implémentent (CB, PayPal) : plus d'exception « non supporté ».
 */
public interface RecurringPayment {
    void recurringCharge(double amount);
}

/** Espèces : paiement ponctuel seulement. Elle n'implémente plus de méthode qu'elle ne sait pas faire. */
public class CashPayment implements PaymentMethod {

    @Override
    public void pay(double amount) {
        System.out.println("Espèces : " + amount);
    }

    @Override
    public void refund(double amount) {
        System.out.println("Remboursement en espèces : " + amount);
    }
}

/** Carte bancaire : paiement ponctuel et prélèvement d'abonnement. */
public class CreditCardPayment implements PaymentMethod, RecurringPayment {

    @Override
    public void pay(double amount) {
        System.out.println("Débit CB : " + amount);
    }

    @Override
    public void refund(double amount) {
        System.out.println("Remboursement CB : " + amount);
    }

    @Override
    public void recurringCharge(double amount) {
        System.out.println("Prélèvement mensuel CB : " + amount);
    }
}

/**
 * Module abonnements : prélève chaque mois tous les abonnés.
 * Il ne reçoit que des RecurringPayment : un paiement en espèces ne peut plus lui être passé.
 */
public class SubscriptionBilling {

    public void chargeAll(List<RecurringPayment> subscribers, double monthlyFee) {
        for (RecurringPayment subscriber : subscribers) {
            subscriber.recurringCharge(monthlyFee);
        }
    }
}

3Le risque inverse : une interface par méthode

On tomberait dans la complexité inutile (sur-ingénierie) : Payable, Refundable, RecurringChargeable… Trois types à nommer, implémenter et injecter pour un seul concept. OrderProcessor recevrait un objet pour payer et un autre pour rembourser, qui pourraient ne pas correspondre au même moyen de paiement (payer par carte, rembourser par PayPal). La notion de « moyen de paiement » disparaîtrait du code (opacité). C'est l'excès inverse de l'interface fourre-tout, et ce que YAGNI déconseille.

Notre découpage, en une phrase : deux interfaces, parce qu'il y a deux clients réels (les commandes et les abonnements) et deux familles de moyens de paiement (ceux qui savent seulement encaisser et rembourser, et ceux qui savent aussi prélever chaque mois) ; pay et refund restent ensemble car tous les moyens les supportent et ils servent le même client.

1Formules (cours, chapitre 2)

  • Ca (couplage afférent) : qui dépend de ce package. Mesure sa responsabilité.
  • Ce (couplage efférent) : de qui ce package dépend. Mesure sa dépendance.
  • I = Ce / (Ca + Ce) : 0 = totalement stable, 1 = totalement instable.
  • A = Na / Nc : 0 = totalement concret, 1 = totalement abstrait.
  • D = |A + I − 1| : distance à la séquence principale (A + I = 1) ; 0 est l'idéal.

Le cours compte Ca et Ce en classes ; l'énoncé ne donne que les flèches entre packages, donc chaque flèche compte pour 1. Exemple pour orders : ui, billing et notifications dépendent de lui (Ca = 3), il dépend de billing et persistence (Ce = 2), donc I = 2 / 5 = 0,40, A = 2 / 10 = 0,20 et D = |0,20 + 0,40 − 1| = 0,40.

Partie 2 · Cohésion et couplage2.2 Couplage : ADP, SDP, SAP

1ADP : le cycle

Cycle : orders → billing → orders. orders dépend de billing, qui dépend de orders.

Conséquence en équipe (« syndrome du lendemain matin ») : l'équipe billing modifie une classe le soir ; le lendemain matin, orders ne compile plus ou ses tests échouent, alors que personne n'y a touché. Avec le cycle, les deux packages forment en fait un seul gros bloc : impossible de les livrer, de les versionner ou de les tester séparément, et chaque changement de l'un oblige à recompiler, retester et redéployer l'autre. ui, qui dépend de orders, hérite de tout le bloc.

Deux corrections possibles :

  1. Inverser la dépendance (DIP) : orders définit l'interface dont il a besoin, par exemple PaymentMethod, et billing l'implémente. La flèche orders → billing disparaît : il ne reste que billing → orders.
  2. Nouveau package : extraire les classes partagées qui créent le cycle (par exemple les données de commande que billing lit) dans un package commun, dont orders et billing dépendent tous les deux.

Choix : DIP. Pas de package de plus à maintenir et à versionner (YAGNI), c'est déjà ce que fait la partie 1 (PaymentMethod est dans orders, billing l'implémente), et cela supprime en même temps la flèche contraire à SDP (question suivante). Avec la solution 2, la flèche orders → billing resterait.

2SDP : dépendances vers un package moins stable

Une flèche respecte SDP si elle va vers un package plus stable, donc de I plus petit.

DépendanceI appelantI cibleSDP

Une seule dépendance pointe vers un package moins stable : orders (0,40) → billing (0,67). orders a trois packages qui dépendent de lui, mais il s'appuie sur billing, plus volatil : chaque changement de billing risque de casser orders, et par lui ui, billing et notifications. C'est la même flèche que celle du cycle.

Les autres flèches respectent SDP, même si certaines restent des problèmes de conception : orders → persistence va bien vers plus stable, mais vers un package concret (question suivante).

3SAP : le package en zone de douleur

persistence : I = 0 (deux packages en dépendent, il ne dépend de rien) et A = 0 (9 classes JDBC concrètes, aucune interface), donc D = 1 : il est tout au fond de la zone de douleur (appelée zone de rigidité dans le cours).

Pourquoi c'est un problème pour ShopFlow :

  • persistence est stable « de force » : orders et billing utilisent directement ses classes JDBC. Pourtant il contient les détails les plus changeants : SQL, schéma des tables, pilote de base de données.
  • Chaque modification de schéma ou de technologie (MySQL vers PostgreSQL, ajout d'un cache) se propage à orders et billing, donc au cœur métier, puis à ui. C'est exactement le « chaque évolution coûte de plus en plus cher » du contexte.
  • Impossible de tester orders ou billing sans une vraie base de données.

Correction (SAP + DIP) : les interfaces de stockage passent dans les packages qui en ont besoin (OrderRepository dans orders, InvoiceRepository dans billing), et persistence les implémente. Il devient alors instable et concret (I = 1, A = 0) : un détail remplaçable, sur la séquence principale.

orders (D = 0,40) et notifications (D = 0,50) sont aussi du côté douleur, mais beaucoup moins loin.

4Graphe corrigé

Code : dossier partie2/

Trois flèches changent, toutes par DIP :

  • orders → billing disparaît : orders possède PaymentMethod, que billing implémente (billing → orders existait déjà) ;
  • orders → persistence s'inverse : orders possède OrderRepository, persistence l'implémente ;
  • billing → persistence s'inverse : billing possède InvoiceRepository, persistence l'implémente.

Comment lire le schéma. Une flèche part d'une classe et arrive sur la classe dont elle a besoin : le package de départ dépend donc du package d'arrivée. Exemple : CardPayment (dans billing) implémente PaymentMethod (dans orders), donc billing dépend de orders. L'inverse n'existe plus : OrderService appelle paymentMethod.pay(order) sans savoir qu'il s'agit d'une carte. Les utilisations à l'intérieur d'un même package (par exemple OrderService qui utilise ses deux interfaces) ne sont pas dessinées.

Le code. Dans le code, une flèche du schéma correspond à un import d'un autre package. orders n'a aucun import : il contient Order, le service et les deux interfaces dont le service a besoin.

// orders/PaymentMethod.java
/**
 * Interface possédée par orders, implémentée par billing (DIP).
 * orders n'importe plus rien de billing : la flèche orders → billing disparaît, et le cycle avec elle.
 */
public interface PaymentMethod {
    void pay(Order order);
}

// orders/OrderRepository.java
/**
 * Interface possédée par orders, implémentée par persistence (DIP).
 * La flèche orders → persistence s'inverse : c'est persistence qui dépend de orders.
 */
public interface OrderRepository {
    void save(Order order);
}

// orders/OrderService.java
/**
 * Cœur métier : passer une commande.
 * Il n'utilise que les interfaces de son propre package : aucun import de billing ni de persistence.
 */
public class OrderService {

    private final PaymentMethod paymentMethod;
    private final OrderRepository orderRepository;

    public OrderService(PaymentMethod paymentMethod, OrderRepository orderRepository) {
        this.paymentMethod = paymentMethod;
        this.orderRepository = orderRepository;
    }

    public void place(Order order) {
        paymentMethod.pay(order);
        orderRepository.save(order);
    }
}

Partie 2 · Cohésion et couplage2.3 Cohésion : REP, CCP, CRP

ScénarioPrincipeCoût actuelRéorganisation
A. Une loi fiscale impose de modifier TaxCalculator (billing), InvoicePrinter (ui) et AccountingExport (exports). CCP : les classes qui changent ensemble vont ensemble (le SRP des packages). Une seule raison de changer, la loi, touche 3 packages : 3 modifications, 3 séries de tests, 3 livraisons à coordonner, souvent entre 3 équipes. En oublier un donne des factures fausses. Regrouper les trois classes dans un package fiscalite, utilisé par billing, ui et exports. La prochaine loi ne touchera que lui.
B. La « Calculatrice Mobile » importe core seulement pour MoneyUtils, alors que core embarque aussi les drivers SQL. CRP : réutiliser une classe, c'est réutiliser tout son package (l'ISP des packages). Pour une seule classe, la calculatrice embarque les drivers SQL : application plus lourde, compilation plus longue, et une nouvelle version de core à intégrer à chaque changement de la partie base de données, qui ne la concerne pas. Découper core en un petit package money (calculs purs, sans dépendance) et un package database (drivers SQL). La calculatrice ne dépend que de money.
C. orders est utilisé par l'équipe mobile sans numéro de version. Vous changez le calcul de la remise. REP : ce qu'on réutilise doit être livré comme une version numérotée. L'équipe mobile reçoit le nouveau calcul sans l'avoir demandé ni testé : les prix changent dans l'application du jour au lendemain. Elle ne peut ni rester sur l'ancien comportement, ni savoir quelle version elle utilise. Publier orders comme un artefact versionné (SemVer) avec un journal des changements. Le nouveau calcul sort dans une version majeure (2.0.0, car le comportement change) ; l'équipe mobile reste en 1.x le temps de migrer, et on maintient la 1.x pendant cette période.

Partie 2 · SynthèseQuestion de synthèse

1Au stade MVP : favoriser CCP

Au début, le métier change sans arrêt et personne d'autre ne réutilise le code. On regroupe donc en peu de gros packages les classes qui changent ensemble : chaque évolution touche un seul package et les refactorings restent rapides. Créer vingt micro-packages versionnés dès le premier mois coûterait cher en coordination pour une réutilisation qui n'existe pas encore (complexité inutile).

2À maturité : refactoriser vers REP et CRP

Quand le projet se stabilise et que d'autres équipes réutilisent ses modules (l'équipe mobile du scénario C, la calculatrice du scénario B), on découpe les packages selon leurs utilisateurs (CRP) et on les livre en versions numérotées (REP), jusqu'à des services autonomes si besoin.

3La tension entre les trois principes

REP et CCP poussent à regrouper (des packages plus gros), CRP pousse à séparer (des packages plus petits). On ne peut pas satisfaire les trois à la fois : en privilégier deux, c'est payer le prix du troisième. La bonne position dans ce triangle change avec la maturité du projet.

ShopFlow, à deux ans, est entre les deux. C'est le travail de ce TP : appliquer SOLID et DIP pour isoler et stabiliser le cœur métier, supprimer le cycle, puis versionner orders dès que l'équipe mobile le réutilise.
